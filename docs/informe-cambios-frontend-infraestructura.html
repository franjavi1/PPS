3. Patrón TablaPrincipal

IMPLEMENTADO

Se creó frontend/src/components/TablaPrincipal/TablaPrincipal.jsx para centralizar búsqueda, ordenamiento, paginación y renderizado de filas.

Comportamientos comprobados

  • Búsqueda global: filtra sobre propiedadesFiltro o sobre las columnas configuradas.
  • Ordenamiento: usa useMemo y localeCompare(..., "es").
  • Valores anidados: admite valorOrden(item) por columna.
  • Paginación: usa slice y permite 10, 25 o 50 filas.
  • Reinicio de página: vuelve a página 1 cuando cambia la búsqueda o el tamaño.
  • Acciones: acepta una función accionesPorFila.
useEffect(() => {
  setPaginaActual(1);
}, [busqueda, filasPorPagina]);

const comparacion = valorA.localeCompare(valorB, "es", {
  sensitivity: "base",
  numeric: true,
});

const inicio = (paginaActual - 1) * filasPorPagina;
return datosProcesados.slice(inicio, inicio + filasPorPagina);

5. Integridad referencial preventiva

IMPLEMENTADO EN UI

Los paneles consultan relaciones existentes antes de habilitar acciones destructivas. El ejemplo del documento está presente en TipoDocumentoPanel.jsx:

const estaAsociado = (id) =>
  personas.some(
    (persona) => persona.td_id === id || persona.tipoDocumentoId === id
  );

<button
  disabled={
    !hasPermission(currentUserRole, "eliminar") || estaAsociado(td.id)
  }
  title={
    estaAsociado(td.id)
      ? "No se puede eliminar: tiene personas asociadas"
      : "Eliminar Tipo de Doc."
  }
>
  Eliminar
</button>

También se observan controles equivalentes en sedes, aulas, comisiones, asignaturas y otros paneles.

La prevención visual evita peticiones innecesarias, pero la base de datos y el backend deben conservar sus restricciones. El frontend nunca debe ser la única defensa de integridad.

6. RBAC y sesión en frontend

PARCIAL / DEMOSTRATIVO

Matriz centralizada

authHelper.js define:

ROLE_ADMIN:      ["crear", "editar", "eliminar", "leer"]
ROLE_INSTRUCTOR: ["editar_notas", "leer"]
ROLE_USER:       ["leer"]

Distribución del rol

  • AuthContext.jsx guarda el token en sessionStorage.
  • auth.js decodifica el payload y normaliza distintos nombres de claim.
  • Navbar.jsx entrega currentUserRole a DesktopNav y MobileDrawer.
  • Los paneles usan hasPermission() para ocultar altas o deshabilitar edición/eliminación.

Menús

El escritorio y el drawer móvil aplican el mismo criterio. Las opciones de lectura se muestran a los tres roles; las opciones de creación se muestran al administrador.

Limitaciones detectadas

  • El login asigna roles según si el texto del usuario contiene “admin” o “instructor”.
  • El token utiliza una firma simulada: mock_signature_key.
  • Los permisos son genéricos y no distinguen recursos.
  • Las rutas declaradas en App.jsx no están envueltas en una guarda central.
  • El backend Flask no valida este token ni estos permisos.
  • sessionStorage puede manipularse desde el navegador.
La frase “asegura que un usuario no pueda realizar operaciones de escritura” debe matizarse: lo evita desde los controles visibles del frontend, pero no impide una llamada directa a la API.

7. Code-splitting y optimización de build

IMPLEMENTADO Y VERIFICADO

El commit 58dcc3e modifica únicamente App.jsx y vite.config.js.

App.jsx

  • Mantiene el Login como importación estática.
  • Convierte las páginas administrativas en importaciones dinámicas con lazy().
  • Envuelve las rutas con Suspense.
  • Muestra “Cargando sección...” mientras llega el chunk.
import { lazy, Suspense } from "react";

const Legajos = lazy(() => import("./pages/Legajos"));
const Personas = lazy(() => import("./pages/Personas"));
const Planes = lazy(() => import("./pages/Planes"));

<Suspense fallback={<div>Cargando sección...</div>}>
  <Routes>...</Routes>
</Suspense>

vite.config.js

  • Configura codeSplitting: true.
  • Agrupa dependencias React en vendor-react.
  • Agrupa las demás dependencias en vendor-helpers.
  • Configura el umbral de advertencia en 600 kB.
manualChunks(id) {
  if (id.includes("node_modules")) {
    if (id.includes("react")) return "vendor-react";
    return "vendor-helpers";
  }
}

12. Conclusión

La rama implementa materialmente los ejes técnicos descritos: componentización, tabla reutilizable, wizards progresivos, controles preventivos, RBAC visual y code-splitting. El resultado de build es reproducible y mantiene el bundle de entrada en 14,39 kB.

La principal precisión necesaria para una presentación es separar control visual de permisos de seguridad real. La rama evita acciones desde la interfaz, pero aún requiere autenticación y autorización verificadas por el backend.

Resultado general: el documento entregado representa correctamente la dirección del trabajo. Este informe ajusta las métricas al build actual y documenta las limitaciones que deben declararse con claridad.
